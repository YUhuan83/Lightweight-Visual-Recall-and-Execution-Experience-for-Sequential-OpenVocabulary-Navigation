## 差异一：探索执行在来源保护前已经分叉

可定位的问题范围是：采样图/候选姿态 → 车辆路径选择 → frontier 退役后的短段交接 → 新意图重算，整体推进不足。需要从实际完整路径、候选比较与退役时机验证，不应关闭 footprint 检查或只延长动作租约。

## 对近期改动的判断边界

224538 与 225946 均没有目标 mask/localization/confirmation，也没有本次新增的 confirmed_approach_failed 状态。新增接近失败交接分支未在两轮中获得现场覆盖；不能拿它解释此前探索停车，也不能因此宣布所有改动绝无回归。相同新版未录像轮仍明显运动，说明“升级后车辆必然动不了”不成立。相同 Native 源既有正常轮也有迟滞轮，说明故障具有运行时条件，不能只靠回滚目标记忆模块解决。

## 追加：为什么三轮都有大量静止

用户进一步问共同原因。以同一420秒窗逐 Native 有效静止间隔交叉匹配 control/plan 状态，防止将两种统计相加重复计时；另外按 query 墙钟截取 stack.log 的实际请求/失败时间。

| 静止时对应的控制状态 | 215010 | 224538 | 225946 |
|---|---:|---:|---:|
| stale_command（没有有效速度需求，包含规划/失败恢复空档） | 119.92s | 93.29s | 214.15s |
| gear_change（制动等待换挡） | 71.87s | 66.10s | 49.33s |
| 上两类占近乎静止时间 | 83.79% | 76.65% | 85.53% |
| 同时处于 stale_command 与 planning | 75.95s | 74.63s | 159.45s |
| 同时处于 gear_change 与 following | 66.93s | 63.99s | 47.53s |

这些交叉项只是各控制类别的子集，不能再与类别总量相加。状态最近邻关联保留原异步边界，不当作精确CPU耗时。

- `graph_path_bridge.py::try_candidate/candidate_failed/on_plan_result` 按候选串行派发，失败后进入下一候选，也可能比较同一端点两种航向；无健康执行段时等待新路径，速度需求过期后 `cmd_vel_to_control.py::tick` 制动。87米轮有54个empty_path候选失败，另1个footprint拒绝；新版未录像31个empty_path，另3个拒绝；录像79个empty_path，另21个拒绝。是候选次数，不是独立任务/目标失败次数。
- 从当前请求到该候选失败的时长中位数分别1.745/1.737/1.641s；包括动作/搜索/检查交接，非纯Smac CPU耗时。多次失败串行累积形成数秒至十几秒停车；后台尝试可与运动并行，不能用失败次数乘中位数充当静止总时长。
- `cmd_vel_to_control.py` 换挡确认默认2.0s，`planning.py::update_direction_shift` 要求反向需求稳定且实测低速才切换；实际launch未覆盖。三轮公开控制状态记录36/34/33段gear_change，中位持续2.047/2.008/2.000s，吻合该软件等待。整段等待含减速和静止，故段数×2不等于纯静止换挡时长；不擅自视每段换向都多余或删除换挡安全条件。
- 87米轮静止中另有29.34s同时对应stale_command与target_evidence_rejected(instance_mismatch)，说明旧接近交接/无新执行需求也占空档；不能将其全归网络。录像轮来源保护又额外对应较长空档，前两轮无该异常仍大量静止，故只修Native不能消除共同停驶。
- 已确认共同机制：可执行路径供应/续接不连续、频繁换向造成固定等待，以及失败后的再规划空档；保护制动是其执行结果。为什么候选频繁不可达、部分换向/退役为何缺乏推进仍需完整候选路径与当前地图闭包；没有因此宣布唯一底层根因或直接改参数。
