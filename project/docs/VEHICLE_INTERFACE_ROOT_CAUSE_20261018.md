# 真实车体接口审计：Smac 平滑边界根因（2026-10-18）

## 结论与范围

已经定位并实施修复一条可重复验证的规划拒绝根因：自定义 Smac 适配层在单独平滑后选择了起始航向变化的后缀，之后连续起点拼接检查拒绝该后缀，却没有返回同次搜索中保留的可行原始后缀。无障碍地图也能复现，因此此反例不依赖 BeamNG 物理、视觉识别或实时消息延迟。

这不能解释所有历史失败。Native 独立接收上下文的间歇延迟、动态转向/制动标定、多方向段交接、地图障碍真值、整体探索进展及视觉到达仍未全部闭环。本轮只进行封闭日志分析和服务器 CPU 隔离验证，没有启动新的整车搜索。

## 最早被违反的约定

链路为：实际后轴位姿 → 连续起点连接曲线 → Smac 离散搜索后缀 → 手动平滑 → 连接拼接与曲率检查 → 路径执行。

`ackermann_smac/src/planner.cpp` 的 `native_plan` 保存同次搜索的 raw 路径，再对副本手动调用 smoother。原选择条件检查平滑成功、内部曲率及碰撞，却遗漏前后边界位姿一致性。封闭 case6/7 中手动平滑改变首航向约 0.0254～0.0917 rad（约 1.5～5.3°）。稍后的拼接要求首航向与连接锚点误差不超过 1e-5 rad，因而拒绝已经选中的平滑后缀；此时没有重试 raw 后缀。

分别从六个原连接锚点调用搜索，raw 后缀及其拼接路线可通过几何/碰撞检查；原包装器却返回 `No safe bounded continuous-start plan`。这是适配层选择顺序的缺陷，不能仅因该异常文字就归为场景障碍。

以往测试覆盖了曲率、碰撞和部分 raw 回退，但没有覆盖“平滑内部合格、边界航向改变、下游拼接失败”这一跨阶段反例。这是此前验证的明确遗漏，不是测试次数能够弥补的。

## 最小修改与影响

- 生产改动仅 `ackermann_smac/src/planner.cpp`：选择 smooth 前同时要求首末位置与 raw 相同（1e-6 m）、首末航向相同（1e-5 rad）；否则走已有的同次搜索 raw 回退。
- 回退仍通过原曲率、完整 footprint 碰撞和预算检查，再接受外层精确连接检查。没有放宽拼接容差、关闭碰撞、改变半径或强改路径姿态，也不追加第二次搜索。
- `ackermann_smac/test/test_planner.cpp` 新增实际插件回归，使用 case6/7 的无障碍控制条件，检查生成路径、精确起点、曲率和全路径 footprint。
- raw 回退可能使路线较不平滑；几何合格不能替代真实车辆动态跟踪验收。

## 真实车体与理想载体的差异核查

切换真实车体同时引入车辆约束规划、方向分段/换挡、速度环和 Native 执行器，并非只改变质量与碰撞。真实车体不能任意原地旋转，更依赖连续起点航向约定，因此上述适配缺陷会暴露。

静止组件已实测后轴坐标车体 front=3.282006、rear=0.908011、half_width=1.000049 m，在当前 footprint 3.4/1.05/1.05 m 内。轮距/后轴及原碰撞状态记录见 `EXECUTION_WAIT_AUDIT_20261018.md`。这只证明静止尺度相容，不证明所有动态参数正确。

当前 wheelbase=2.501 m、标称转角 0.54 rad、输入上限 0.6 的模型估算最小半径约 7.447 m；控制约束 8 m，规划 12 m。输入到实际曲率、制动距离、低速起步仍须实测。两份封闭轨迹按稳定转向条件筛选，没有足够合格窗口，结果为 null；不能当作参数正确或错误的证据。

消息链方面，151920 同源帧在三旁路快速收到而 Native 上下文间歇晚到，问题已收窄但尚未确定 DDS 接收前还是回调调度等待。当前 Humble 默认 Python executor 丢弃底层 take_message 的接收元信息，不能直接给普通回调增加第二个 MessageInfo 参数。没有据此擅改 QoS 或延长控制命令期限。该问题与本次无障碍 CPU 规划反例独立。
