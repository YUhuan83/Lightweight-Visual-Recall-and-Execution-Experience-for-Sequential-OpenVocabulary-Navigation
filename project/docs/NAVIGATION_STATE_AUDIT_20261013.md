## 修复依赖顺序与必须验证的反例

1. **统一动作/服务事务生命周期（S01/S02/S03）**：明确请求、活动动作、替换和已消费终态的身份与期限。迟到接受只能处置所属请求；终态退休不能破坏替换期间的deferred结果。缺响应只算执行/接口失败，不算目标已到达或记忆候选不可达。
2. **统一恢复归属和实际候选可行性（P01/P02）**：首次下发前接入失败归候选，不误记作已经执行失败；cusp拒绝计入有实际进展重置的统一预算，不能靠新路径或新时间戳无限续命。仍保留下发时当前pose/双图复验。
3. **统一几何与控制参数契约（P03/P04/G01）**：记录搜索、平滑前后、下发的对应路径与实际pose；核对RPP实际前视、goal checker、曲率和端点完成区域。在无障碍有限半径模型及真实C++回放中验证，再加动力学。
4. **补齐运动区域可通行证据（T01）**：让规划与图的terrain约束共享语义、坐标和有效范围；未知区域不能被无条件视为已证可通行。方案须同时评估误拒绝、清除更新和真实转弯空间，不硬缩通道或给Town写专用绕行。
5. **独立查引擎与退出故障（E01/E02）**：保留请求级/引擎/资源见证；不要靠放宽超时掩盖响应空档。

每项修复必须覆盖正常、消息缺席/迟到/重复、取消/目标切换、恢复和跨阶段交接。替换请求超时尤其不能简单恢复旧动作：服务端可能已接受新动作而ACK丢失，须明确动作UUID/取消权限、实际控制停止及状态归属。禁止凭空确认成功、扩大停车盘或移除物理来消除日志失败。
