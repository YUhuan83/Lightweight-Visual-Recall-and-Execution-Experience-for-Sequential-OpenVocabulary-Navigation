## 已复现的交接缺口

现场查询相对时间：

1. 98.8158秒，开始为旧 owner `241fffcb…:10` 比较4个候选。
2. 100.0442秒，C++退役旧 owner，reason=frontier_resolved。
3. 100.0558秒，新 owner `3a281823…:11` 的 route_status 和4点 Path已记录，目标(726.8903,-55.4098)。
4. 100.1481秒，桥仍发送旧 owner 的选择。C++当前owner已不同，accept_vehicle_choice 直接返回，没有ACK。
5. 100.1504秒，桥报告旧 owner退役。直到104.9952秒同新owner再次发Path，104.9999秒才恢复规划。该段桥状态空等4.8495秒；整次近停98.547–106.954秒，8.407秒。

源码机制：on_route 在 frontier_choice 等待期间先返回，另一owner的新路线没有进入latest_route；若新路线较早在比较pending期间到达，则可先进入latest_route，但旧owner退役调用reset后又将其清空。reset正确撤销旧动作的同时丢失了新意图，恢复依赖下一次图路线发布。

两条生产回调反例已复现，2项均失败/0错误：新路线在选择等待期间到达、或在旧比较期间先暂存，然后旧owner退役，最终两者的新路线都丢失。counterexample_route_retirement.py / residual_owner_counterexamples.log。这是待修缺口；不能将有意保留的失败说成回归通过。

原bag没有桥端逐回调入口/出口，无法百分百还原现场两个订阅的处理顺序。现场已有新Path而桥等到下次发布、两种顺序可复现丢失与源码一致，是强证据；不声称已做原私有队列逐事件精确回放。

已排除本段“需要等图源戳变新才授权”的初始猜测：C++ plan_to_goal 已用自身now发布Path。正常选择ACK与新路线相隔毫秒，本段是旧owner已退休而选择无ACK、路线交接丢失，不能通过放宽新鲜度修复。
