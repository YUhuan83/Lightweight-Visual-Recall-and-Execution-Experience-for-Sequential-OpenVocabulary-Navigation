# 探索走停：候选选择与执行段数约定一致（2026-10-21，离线）

用户当前只要求修复车辆实际走走停停；服务器不可用，本次没有连接服务器。

## 已复现的问题

现有 `max_motion_sections=6` 只在 `execute_checked_path` 派发前检查。
`frontier_path_issue` 和普通航向候选比较没有该条件，因此比较阶段可以选中
执行阶段必然拒绝的多段路径，丢掉已找到的可执行 frontier 候选，增加无效规划。
这是已有段数限制的数据流不一致；不把它当作历史所有走停的根因。

新增四项反例在改前源码均断言失败、零加载错误：高收益超限候选错误胜出；
所有比较候选超限仍发布选择；普通航向候选在拒绝前被缓存；替代航向超限未走
候选拒绝流程。最初一次测试指定了错误类名，加载错误日志单独保留。

## 修改

- `graph_path_bridge.py` 提取已有规则为 `exploration_motion_issue`，在普通
  规划结果进入航向比较之前检查；派发前沿用同一规则。
- `exploration_cost.py` 在 frontier 候选准入及最后重新核验时调用同一规则。
- 保留原默认6段及语义收益评分。物体、记忆、恢复和运动中扩展不新增该限制；
  全部比较项失败时恢复普通候选，不直接拒绝整条图路线。
- 未修改 Smac、connector、车体、速度、换挡等待或碰撞检查。
