# 2026-10-13 离线路径执行审计

本轮遵从“现在离线检测，彻查原因”：没有重新连接服务器，没有改动导航、控制、物理或传感器运行代码。新增可重复运行的诊断程序、诊断测试及本记录。必要现场验收未通过，不创建 Git commit。

## 结论与边界

当前最明确的执行故障在 **Smac 返回路径、GraphPathBridge 的实际姿态接续、RPP 的受限转向和换向停车判定之间**。这几个环节各自通过部分检查，却没有共同保证“车辆从允许的上一段结束姿态，能完成下一段”。

记录中的短倒车段，在零通信延迟、瞬时转向、无障碍的理想自行车模型中也会错过停车范围；同一路段从规划的名义姿态出发能够到达。因此，这一具体反例不需要 BeamNG 的轮胎、地形、模型负载或通信延迟就能出现。它不代表所有历史失败都由同一个原因造成。

同时确认两种会放大停驶/重规划的代码行为：换向接续失败绕过已有重试计数；首次下发前的接续不可行被归入执行失败，未继续检查剩余规划候选。已取回的另一条 Smac 返回路径还可重放出曲率契约拒绝。引擎多路请求共同延迟是独立存在、尚未定根因的问题。

视觉记忆的原理没有被这些执行反例否定。发生问题的服务器组件测试没有启动视觉模型，离线回调中的 query 和 memory 也为空；共同的执行链就足以产生问题。这不等于视觉记忆及完整多目标流程已经验收成功。

## 1. 短换向段：上一段“到达”不保证下一段可执行

涉及 `nav2_adapter/wildos_nav2_adapter/motion_path.py:51`、`graph_path_bridge.py:1493`、`ackermann_rpp/src/controller.cpp:107`、`nav2_adapter/config/nav2_ackermann_control.yaml:53`。

历史 `execution_continuation/cusp3` 的第二段约 1.706 m，为单向倒车段。保存的三个新鲜 SDK 样本位于下发时刻前后，**并不是 GraphPathBridge 该回调使用的精确 odom**。旧版本未记录精确回调姿态，因此结论保留这一限制。

| 检查 | 离线结果 |
|---|---|
| 相对上一换向点的位置误差 | 约 0.172 m，处于 0.2 m 到达范围内 |
| 朝向误差 | 约 0.140 rad，约 8°，处于 0.35 rad 到达范围内 |
| 旧接续预测 | 接受，但预测终点偏差 0.20737～0.21009 m |
| 换向停车要求 | 位置误差 ≤0.2 m，朝向误差 ≤0.35 rad，还需实际停稳 |
| 零延迟理想自行车重放 | 三个样本均未进入停车范围；最近距离 0.20730～0.21001 m，随后前视目标越过运动方向，触发方向保护 |
| 名义起点对照 | 同一路段进入停车范围，位置误差约 0.19805 m |

重放只使用短段终点作为 carrot、`2*y/(x*x+y*y)`、8 m 曲率限制及本项目的方向/端点判断。它没有运行真实 C++ 插件、TF、速度调节、碰撞图或 BeamNG。因为这一短段始终小于 3 m 最小前视距离，该条件下终点 carrot 的简化有明确依据。

将 2 mm 积分步长分别改成 1 mm、5 mm，以及旋转/平移整个坐标系，失败结论不变。再用正式三维 `body_rotation` 和 `SBR_BASE_OFFSET` 重算后轴，和原二维近似的差别只有约 0.17～0.19 mm，仍然失败。该反例不能归因于后轴偏移近似产生了厘米级误差。

当前代码已经包含上一阶段的候选修复：短段终点预测使用实际 goal checker 的 0.2 m，而不是统一 0.6 m。本轮重放确认三个旧反例均被提前拒绝。

**这个修改只是提前阻止不可行下发，并没有生成能成功到达的新路径。** 将 `replanning_after_maneuver` 当成修复成功是不成立的。还需要候选选择和有进展的恢复机制配合。

## 2. 换向接续失败没有统一的恢复预算

涉及 `graph_path_bridge.py:1534`。这一分支清空队列和旧起点缓存后，直接调用 `start_segment()`；没有更新 `recovery_attempts`，没有设置 `blocked_endpoint` 或退避。

使用真实生产回调、ROS 接口替身和空障碍图，注入同一接续拒绝 8 次：

- 8 次都再次调用 `start_segment()`。
- `recovery_attempts` 始终为 0，`blocked_endpoint` 始终为空。
- 没有发送 FollowPath 动作；原来的碰撞、方向与曲率保护仍然生效。

这是**分支预算的离线反例**。测试有意重复注入同一交接事件，并模拟规划入口；没有假装车辆在服务器上自主循环了 8 次。源码中的普通执行失败重试上限不覆盖这一入口，组件测试脚本自己的次数上限也不能约束正式导航。

修复方向：以目标/实例、路线和实际进展为归属，统一管理接续恢复预算；只有真实进展才重置。一次合理的姿态接续重规划应允许，但重复相同失败必须进入有界退避或候选切换。不能把所有换向重规划一概禁止，也不能仅在测试脚本中加上限。

## 3. 候选可行性检查发生得太晚，失败归属不合理

涉及 `graph_path_bridge.py:1401`、`:1512`、`:1531`。

当前顺序是：验证名义路径 → 比较少量候选的长度/换向代价 → 选定路径 → 才验证实际后轴姿态能否接入。若首次发送前不能接入，就调用 `follow_failed('motion_section_invalid')`。

离线回调中设置两个候选，再给第一个候选输入上述已知接续反例，结果是：

- FollowPath 实际发送数量为 0。
- 状态变为 `follow_failed`，整条路线进入 2 秒退避。
- `candidate_index` 仍为 0，继续尝试候选的调用次数为 0。

该测试没有证明第二个候选可行；它证明现有分支没有尝试它。相同环境下重试仍可能选回同一条名义代价较小、实际不可接入的路径，从而消耗执行重试机会。

修复方向：将实际姿态接续检查纳入候选接收/比较，失败时由规划候选状态机处理；实际接受动作后的跟踪失败才进入执行恢复。下发前仍应保留新鲜姿态、地图与健康复核，避免候选检查和实际发送之间发生变化。

## 4. Smac 的成功返回与下游车辆路径约束不一致

证据为已取回归档 `test_artifacts/server_validation_20261012/direct_steering_evidence.zip` 中的 `direct_steering_curve1/execution/result.json`，SHA256：

`d5ecfe949c0d29bb134ad81ee3a740ff668f6fd56ed245c47187075511872462`

该路径 55 姿态，规划动作状态为 4（成功）。把同一形状平移到足够大的全空障碍图，保持朝向、间距、8 m 半径和现行正式校验器，仍得到 `excess_curvature`。原冻结诊断的 16～20 窗口：约 2.11766 m 上朝向变化 0.37096 rad，校验值约 0.17517/m，超过 0.125/m。

`ackermann_smac/src/planner.cpp` 包装层检查起点、预算和碰撞；普通分支仍返回上游 Smac 路径，没有在插件内部保证与 Python 下游相同的曲率/接续契约。现有“连续起点接续”只在起点量化后碰撞时触发，不能解决所有无碰撞但运动接续困难的起点。

不能据此宣布道路没有可行路线，也不能直接断定 Smac 搜索算法有缺陷。记录缺少这次同一规划请求的平滑前路径，无法区分量化朝向、解析接续、平滑输出或下游解释的具体贡献。上游参考源码默认 `smooth_path=true`，此前现场读取也为 true；不能假设平滑已经关闭。下一次需要冻结原始、平滑后及分段后的同一请求，逐段比较几何与姿态含义。

修复方向：明确路径位置、车体朝向、方向和曲率的一致约定，对生产者/消费者采用相同反例验证。禁止靠放宽半径校验或删除方向保护把不一致掩盖掉。

## 5. 走入草地/灌木有另一条独立机制

当前两张 Nav2 costmap 都接入了障碍点云，FollowPath 碰撞检查也已经开启；“完全没接障碍”的旧结论不适用于当前配置。

但 costmap 插件仍只有 `obstacle_layer` 和 `inflation_layer`，`track_unknown_space=false`。WildOS 的 terrain/traversability 影响图和候选选择，当前 Nav2 地图没有对应地形可行性图层。图路线约束的默认横向范围为 `2*R + 3.4 = 19.4 m`，路径评分只有较弱的偏离图路线代价。

新的合成反例是一条满足 8 m 转弯半径、离图边最远 8 m 的半圆路径：在全空障碍图中正式路径校验接受；给同一路径上的格子标为障碍后则拒绝。这个测试没有指定草地标签，也不证明某次实际草丛漏检；它证明“图边被选为可通行”不会自动把附近大范围运动曲线也约束在已经确认可通行的区域。

因此，当灌木/地形没有形成有效障碍标记时，恢复真实碰撞只能让车在执行时碰撞或受困，不能自动补上规划中的地形约束。下一步应对齐可行区域、未知区域及传感器覆盖的表达，不能简单把 19.4 m 通道缩窄到车辆无法转弯。

## 6. 时间戳、坐标与引擎问题分别核对

本轮当前代码的坐标/时钟相关 32 项检查通过。正式 Adapter 保留：后轴位置和 `omega × r` 速度修正；导航平面使用同 XY、z=0、仅 yaw 的 `nav_base_link`；点云保持测量时间及坐标变换；重复/旧测量不会正常续新鲜度。转向符号、目标 query 握手、健康终态和租约旧修复没有在本轮被撤回。

这些测试不能证明现场永无延迟。已取回请求级证据仍显示过：Native 遥测和控制请求各约 2.002 s 超时，独立传感器请求约 4.784 s，GE 请求约 0.896 s。该组件未启动视觉模型，因此没有证据将空档归因于 VisualMemory 或 RADIO 的负载。

现有证据能定位到多条客户端请求共同响应延迟，不能继续区分引擎主线程、渲染、物理或操作系统调度。车端租约已有一次实际移动故障停车验证，但它处理的是失效后果，不是引擎空档根因。旧原生崩溃及独立 costmap 诊断退出异常仍未解决。

还有一项长路径检查范围缺口：接续预测默认使用固定 3 m，而 RPP 配置允许随速度在 3～6 m 间改变前视距离。停止后的短 cusp 使用最小值，当前短段反例不依赖这一点；移动中路径替换需要专门核对相同前视/速度条件，不能用当前短段检查推断长曲线全部可执行。

## 7. 上次 cusp4 的失败阶段不能误归因

用户切换离线前已读取的服务器日志显示，`cusp4` 在 `/wildos/native_control_status` 发布者数量断言失败，尚未进入选路和运动。工具要求该话题恰有一个发布者，但没有记录实际数量、发现端点或等待发现的过程。

因此这次既不能说明修复后的换向失败，也不能认定是 Native 进程崩溃、DDS 发现延迟或残留双发布者。之前日志有 Native 接入成功和退出记录；具体数量仍未知。其原始完整目录尚未取回，本机 `cusp4_readback.json` 仅保存已读取结果摘要，不能当成完整原始归档。

工具改法应为：记录端点身份和数量；对尚未发现的正常启动给有界等待；重复执行器立即拒绝；所有门关闭时完成检查。诊断工具失败和车辆执行失败必须分开统计。
